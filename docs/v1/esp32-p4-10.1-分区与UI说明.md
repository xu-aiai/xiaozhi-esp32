# ESP32-P4 10.1 分区与 UI 说明

本文针对 Waveshare `esp32-p4-wifi6-touch-lcd-10.1` 当前仓库配置，说明分区用途、当前空间占用、APP 区为什么紧张，以及当前 UI 的背景图和表情区行为。

## 一、当前实际生效的分区表

当前 `sdkconfig` 中生效的是：

- `CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions/v2/32m.csv"`

对应实际解析结果如下：

| 分区名 | 类型 | 起始偏移 | 大小 | 用途 |
| --- | --- | --- | --- | --- |
| `nvsfactory` | `data/nvs` | `0x9000` | `200K` | 出厂或预置 NVS 数据 |
| `nvs` | `data/nvs` | `0x3b000` | `840K` | 运行期配置数据，常见如 Wi‑Fi、OTA URL、设置项 |
| `otadata` | `data/ota` | `0x10d000` | `8K` | OTA 元数据，记录当前启动槽位 |
| `phy_init` | `data/phy` | `0x10f000` | `4K` | PHY 初始化数据 |
| `ota_0` | `app/ota_0` | `0x200000` | `4M` | 应用固件槽 0 |
| `ota_1` | `app/ota_1` | `0x600000` | `4M` | 应用固件槽 1 |
| `assets` | `data/spiffs` | `0xa00000` | `16M` | 资源分区，存放背景图、GIF、字体、语音命令模型等 |

说明：

- 当前是 `32MB flash` 布局，不是之前那份 `16m_custom_ui_wakeword.csv`。
- 两个 `app` 槽位各 `4M`，用于 OTA A/B 升级。
- `assets` 单独占 `16M`，所以背景图、表情 GIF、字体、语音模型主要不挤占 APP 区。

## 二、各分区的使用场景

### 1. `nvsfactory`

适合放：

- 出厂默认配置
- 序列号、设备初始化参数
- 第一次启动所需的持久化值

### 2. `nvs`

适合放：

- Wi‑Fi 配网信息
- 主题、亮度等设置
- OTA 下载地址
- 其他运行期持久化配置

特点：

- 小数据、键值型存储
- 不适合放大图片、大模型或频繁整体覆盖的大文件

### 3. `otadata`

作用：

- 记录当前应从 `ota_0` 还是 `ota_1` 启动
- OTA 成功/失败状态切换依赖它

### 4. `phy_init`

作用：

- 无线 PHY 初始化所需数据

### 5. `ota_0` / `ota_1`

作用：

- 存放完整应用固件 `xiaozhi.bin`
- 一边运行当前槽位，一边把新版本写入另一槽位，实现 OTA 双分区升级

特点：

- 这里放的是代码、静态链接后的库、只读常量、部分编译进 ELF 的数据
- 资源图片和 GIF 不应大量塞进这里，否则会直接压缩 APP 可用空间

### 6. `assets`

作用：

- 当前项目的自定义背景图
- 自定义 GIF / 表情资源
- 字体资源
- 语音识别相关模型和配置打包产物
- `index.json` 等资源索引

特点：

- 当前项目把 UI 资源和语音模型都尽量放在这里
- 改背景图、GIF、字体时，主要影响这个分区，不会显著挤压 APP 区

## 三、当前构建产物的占用情况

当前构建目录里可以看到：

| 文件 | 大小 | 对应分区/用途 |
| --- | --- | --- |
| `build/xiaozhi.bin` | 约 `3.9M` | `ota_0` / `ota_1` 里的应用镜像 |
| `build/generated_assets.bin` | 约 `9.2M` | `assets` 分区资源镜像 |
| `build/bootloader/bootloader.bin` | 约 `18K` | bootloader |
| `build/partition_table/partition-table.bin` | 约 `3K` | 分区表 |
| `build/ota_data_initial.bin` | 约 `8K` | OTA 元数据初始镜像 |

编译日志中的关键提示：

- `xiaozhi.bin binary size 0x3f0b40`
- `Smallest app partition is 0x400000 bytes`
- `0xf4c0 bytes (1%) free`

结论：

- APP 区是真的很紧，当前只剩约 `1%`。
- Assets 区当前约 `9.2M / 16M`，还有明显余量。

## 四、为什么 APP 区紧张

### 1. 不是这次两张背景图导致的

这次背景图都放在 `assets` 分区：

- `xcmg_background.rgb565`
- `xcmg_background_idle.rgb565`
- `xcmg_background_active.rgb565`

每张图是 `400x640 RGB565`，固定 `512000` 字节，打进的是 `generated_assets.bin`，不进入 `xiaozhi.bin` 主应用镜像。

### 2. 这次代码改动对 APP 的增量很小

前一版构建日志里：

- `xiaozhi.bin` 大小约 `0x3f0130`

这版构建日志里：

- `xiaozhi.bin` 大小约 `0x3f0b40`

差值约：

- `0xA10`，也就是大约 `2576` 字节

这说明这次“背景状态切换 + 去表情区”的代码改动只让 APP 多了几 KB，不是主要矛盾。

### 3. 真正挤占 APP 区的是应用本体

当前应用镜像包含了比较多功能和组件，例如：

- LVGL / MIPI LCD 显示链路
- 音频编解码与音频服务
- WebSocket / MQTT / OTA / MCP
- Hosted Wi‑Fi 相关组件
- 摄像头和视频相关组件
- 自定义唤醒词、音频处理流程
- 各类 board、codec、network、driver 逻辑

这些都在 `xiaozhi.bin` 里，所以 APP 区紧张是“应用本体功能较多”的结果，不是这次资源图切换造成的。

## 五、当前背景图与表情区状态

### 1. 初始化背景为什么之前看起来没生效

之前的问题是：

- `display->SetupUI()` 比 `assets.Apply()` 更早执行
- 背光打开前，UI 先按默认主题初始化
- 自定义背景图属于 `assets` 资源，应用时机偏后

结果就是：

- 启动早期看到的不是你指定的 `1.png`
- 要等 assets 应用之后，界面才切到自定义背景

### 2. 现在的修正

已经改成：

- `SetupUI()` 后立即执行一次 `assets.Apply()`
- 然后立刻设置 `BackgroundState::Idle`
- 这样背光亮起前就有机会拿到自定义待机背景

### 3. 表情区是否还存在

之前存在。

当前界面里底部圆形 AI / GIF 区域，对应代码里的：

- `emoji_box_`
- `emoji_label_`
- `emoji_image_`

它原本会：

- 创建一个居中的表情显示盒子
- 默认尝试加载 `neutral` GIF
- 在 `SetEmotion()` 时切换 GIF 或图标

### 4. 当前处理

因为当前 UI 不需要表情包，我已将其改为默认关闭：

- `kEnableEmojiBox = false`

效果上：

- 不再显示底部表情包区域
- 不再在启动阶段加载默认 `neutral` GIF
- 状态切换不再依赖表情展示

## 六、背景图当前约定

当前约定如下：

- 初始化 / 激活 / 待机 / 连接中：使用 `1.png`
- 聆听中 / 说话中：使用 `3.png`

落地到资源文件后：

- `xcmg_background.rgb565`：当前默认背景，内容与 `idle` 相同
- `xcmg_background_idle.rgb565`：待机图
- `xcmg_background_active.rgb565`：活动态图

主题名会带前缀，因此最终 assets 中实际查找的是：

- `light_xcmg_background_idle.rgb565`
- `light_xcmg_background_active.rgb565`
- `dark_xcmg_background_idle.rgb565`
- `dark_xcmg_background_active.rgb565`

## 七、后续建议

### 1. 如果要继续扩功能

优先关注 APP 区，而不是背景图资源。

### 2. 如果要给 APP 区腾空间

可优先排查：

- 是否真的需要摄像头和视频组件
- 是否可以裁掉部分协议/模块
- 是否有未使用但被强链接进来的组件
- 是否能精简某些板级公共能力

### 3. 如果只改 UI 资源

优先放在 `assets` 分区：

- 背景图
- GIF
- 字体
- 索引 JSON

这种改法对 APP 区影响最小。
